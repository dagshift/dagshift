# dagshift rules

Generated by `tools/gen_rules_doc.py`; every example below is run through dagshift when the page is built.

Severity says what happened to a finding:

* **fixed**: rewritten, behaviour preserved
* **manual**: breaks on the target and has no safe rewrite; a recipe is attached
* **warn**: still imports, but behaves differently on the target
* **info**: worth knowing before cutover

Rules only fire when they matter for the upgrade you picked. 2.7 to 2.10 gets the 2.x deprecations;
2.10 to 3.3 gets those plus the Airflow 3 changes; 3.0 to 3.3 gets what changed inside Airflow 3.

Turn a rule off with `--ignore DS102`, `ignore = ["DS102"]` in `[tool.dagshift]`, or
`# dagshift: ignore[DS102]` on a line.

## DS4xx Metadata database access

### DS401

`metadata-db-access`: ORM sessions/models used from DAG or task code (blocked from Airflow 3).

Applies to: upgrades whose target is Airflow 3.0 or newer.

Example, Airflow 2.10 to 3.3, `dags/etl.py`:

```python
from airflow.models import TaskInstance
from airflow.utils.session import provide_session

@provide_session
def failures(session=None, **context):
    return session.query(TaskInstance).filter(TaskInstance.state == "failed").count()
```

> **manual**, line 5: `failures` reads or writes the metadata DB directly (TaskInstance). Airflow 3 blocks database access from task code; this fails at run time, not at parse time.
>
> How to fix: Task-instance state: context['ti'].get_task_states(dag_id=..., run_ids=[...]) or get_ti_count(dag_id=..., states=[...]).

### DS402

`db-backed-methods`: dag_run.get_task_instances(), ti.current_state() and similar ORM methods.

Applies to: upgrades whose target is Airflow 3.0 or newer.

Example, Airflow 2.10 to 3.3, `dags/etl.py`:

```python
def check(dag_run, **context):
    return [ti.task_id for ti in dag_run.get_task_instances()]
```

> **manual**, line 2: `dag_run.get_task_instances()` hits the metadata DB, which task code cannot reach in Airflow 3.
>
> How to fix: Ask the Task SDK instead of the ORM. Inside a task:
>
> ```text
>     ti = context['ti']
>     states = ti.get_task_states(dag_id=ti.dag_id, run_ids=[ti.run_id])[ti.run_id]
>     failed = [t for t, s in states.items() if s == 'failed' and t != ti.task_id]
> Signature on Airflow 3.3: get_task_states(dag_id: 'str', map_index: 'int | None' = None, task_ids: 'list[str] | None' = None, task_group_id: 'str | None' = None, logical_dates: 'list[datetime] | None' = None, run_ids: 'list[str] | None' = None) -> 'dict[str, Any]'
> ```

## DS5xx Behaviour changes

### DS501

`guarded-imports`: try/except ImportError around Airflow imports hides breakage.

Applies to: any upgrade (the knowledge base decides per target what is removed or deprecated).

Example, Airflow 2.10 to 3.3, `dags/etl.py`:

```python
try:
    from airflow.operators.bash import BashOperator
except ImportError:
    from airflow.operators.bash_operator import BashOperator
```

> **warn**, line 1: Airflow imports are wrapped in try/except: if one of them is missing on Airflow 3 the except branch runs silently and the DAG imports with fallback objects (often a no-op decorator), failing later at run time instead of at parse time.
>
> How to fix: Guard only the 'is Airflow installed' check (e.g. `import airflow` alone inside the try), or catch ImportError and re-raise when running under Airflow. dagshift has rewritten the imports inside the block; run `dagshift validate` to confirm they resolve.

### DS502

`parse-time-values`: now()/time()/uuid4() evaluated at parse time create a DAG version per parse.

Applies to: upgrades whose target is Airflow 3.0 or newer.

Example, Airflow 2.10 to 3.3, `dags/etl.py`:

```python
from datetime import datetime
from airflow import DAG

with DAG("etl", start_date=datetime(2024, 1, 1), schedule="@daily",
         tags=[datetime.now().strftime("%Y%m%d")]):
    pass
```

> **warn**, line 5: `datetime.datetime.now()` is evaluated every time the DAG file is parsed. Airflow 3 versions DAGs, so a value that changes on each parse creates a new DAG version each time (and in Airflow 2 it was already non-deterministic).
>
> How to fix: Use a fixed value, or compute it at run time: in a templated field ('{{ data_interval_end }}', '{{ macros.datetime.now() }}') or inside the task callable.

### DS503

`schedule-semantics`: Cron/timedelta schedules use trigger timetables in Airflow 3: logical_date and ds shift.

Applies to: upgrades from Airflow 2 to Airflow 3.

Example, Airflow 2.10 to 3.3, `dags/etl.py`:

```python
from datetime import datetime
from airflow import DAG
from airflow.operators.bash import BashOperator

with DAG("etl", start_date=datetime(2024, 1, 1), schedule="30 4 * * *", catchup=False):
    BashOperator(task_id="load", bash_command="load.sh {{ ds }}")
```

> **info**, line 5: Schedule '30 4 * * *': Airflow 3 runs it with CronTriggerTimetable, so a run's logical_date is the trigger time instead of the start of the interval, and data_interval_start == data_interval_end. Nothing in this file reads those values.
>
> How to fix: To keep Airflow 2 semantics: run dagshift with keep_cron_data_intervals=true (wraps the schedule in a *DataIntervalTimetable), or set [scheduler] create_cron_data_intervals = True for the whole environment (Cloud Composer: airflow_config_overrides 'scheduler-create_cron_data_intervals' = 'True') before the first Airflow 3 run.

### DS504

`plugins`: Flask/FAB plugin views and plugin attributes the target removed.

Applies to: upgrades whose target is Airflow 3.0 or newer.

Example, Airflow 2.10 to 3.3, `plugins/acme.py`:

```python
from airflow.plugins_manager import AirflowPlugin
from flask import Blueprint

bp = Blueprint("acme", __name__)

class AcmePlugin(AirflowPlugin):
    name = "acme"
    flask_blueprints = [bp]
```

> **manual**, line 8: Plugin attribute `flask_blueprints` is a Flask/FAB UI extension. The Airflow 3 UI does not render it; it only works with the FAB provider's legacy views.
>
> How to fix: Port it to fastapi_apps, external_views and react_apps on Airflow 3.3, or install apache-airflow-providers-fab and use FabAuthManager to keep the legacy view.

### DS505

`templated-file`: Jinja in code positions; rendered values are not visible to static analysis.

Applies to: any upgrade (the knowledge base decides per target what is removed or deprecated).

Example, Airflow 2.10 to 3.3, `templates/table_dag.py.j2`:

```jinja
from airflow import DAG
from airflow.operators.bash_operator import BashOperator

with DAG("{{ name }}", schedule_interval="{{ schedule }}") as dag:
{% for t in tables %}
    BashOperator(task_id="load_{{ t }}", bash_command="load.sh {{ t }} {{ '{{' }} ds {{ '}}' }}")
{% endfor %}
```

> **info**, line 1: Jinja template: 2 Jinja construct(s) in code positions were kept as-is. Values your generator injects there (schedules, operator classes, kwargs) are only visible after rendering.
>
> How to fix: Render the templates and run `dagshift check` on the output, or use `dagshift validate --render-cmd '<your build command>'`.

### DS803
